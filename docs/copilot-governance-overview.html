Deployment Modes

Three Ways to Govern

The platform operates across local developer tooling, GitHub automation, and an optional visibility layer — meeting teams where they work without requiring a new process.

Local Developer CLI

Validate governance, preview prompt rewrites, run dry-run syncs, and catch compliance issues before they reach a PR — entirely from the terminal with copilot-gov.sh.

GitHub PR Automation

Central governance synced to target repositories through PR-based automation. Drift detection, manifest-tracked removals, and override preservation on every sync cycle.

Evidence & Reporting

Metadata-only local events, reconciliation tooling and weekly evidence templates are implemented. A privacy-approved central collector and dashboard remain external prerequisites.

Core Capabilities

What the Platform Does

Eight interlocking capabilities that together make AI-assisted development safe, consistent, and auditable across every team in the organization.

Instruction Sync

Central governance baseline synced to every target repo. Manifest-tracked so removed files are cleaned up on the next cycle — no orphaned rules.

Prompt Interception

Eligible prompt hooks are evaluated by the interception kernel. Canary-verified delivery paths count as governed; contract-only and unsupported paths are reported separately. Replacement paths preserve developer wording verbatim.

Security Guardrails

Non-negotiable guidance: no hardcoded secrets, no PII logging, no auth bypass, and OWASP injection prevention. All seven prompt rules remain shadow-only pending evidence.

Code Quality Gates

Automated guardrails against unwanted console logs, debug artifacts, and common linting anti-patterns — 80% reduction in review comment noise targeted.

Local CLI Tooling

Developers run doctor, validate, audit, and rewrite locally. Token budget enforcement and placeholder detection happen before the pre-commit hook.

Reusable Workflows

14 approved .prompt.md workflows for common fixes — security findings, test failures, build errors, and migrations. Token and task impact remains a measured pilot hypothesis.

Override Safety

Repo-specific override sections are always preserved across sync cycles. Overrides can extend rules but cannot weaken security, compliance, or testing guardrails.

Audit & Reporting

Governance drift detected within one sync cycle. CODEOWNERS gates every governance PR. Telemetry tracks interception events, deny-rule hits, and workflow usage.

Platform Architecture

Design at a Glance

Key structural decisions and the reasoning behind them — from the central baseline to the interception kernel to the override model.

Platform
Copilot Governance Platform — hybrid governance and prompt optimization, deployed via the naresh-fd/copilot-governance central repository.
Purpose
Reduce repeated AI token usage, enforce secure coding guardrails, and give teams reusable prompt workflows for common fixes.
Governance Files
copilot-instructions.md (repo-wide baseline)  ·  instructions/*.instructions.md (path-specific packs)  ·  prompts/*.prompt.md (approved workflows)
Sync Engine
PR-based sync from the central repo to each target. A .copilot-governance-manifest tracks what was shipped so deleted files are cleaned up on the next cycle without touching repo-added content.
Interception Kernel
prompt-core/ and hooks/ verify an Ed25519-signed pack, evaluate independent rule states, preserve developer wording exactly once on replacement paths, and emit metadata-only audit events. All seven rules remain shadow-only pending approved evidence.
Security Layer
No hardcoded secrets, no PII logging, no bypass of auth or compliance gates, OWASP injection prevention, and secure error handling are injected as guidance; blocking is not yet enabled.
Override Model
A central managed section (between governance markers) is owned by this repo. A repo override section is always preserved. Overrides may add local context but cannot weaken security or compliance rules.
CLI Commands
doctor · validate · audit ·  sync --dry-run · sync --apply ·  prompt <name> · rewrite "<text>" ·  report · install-hooks

Security

Non-Negotiable Guardrails

These rules are injected and evaluated at the prompt layer in addition to code review. All seven remain shadow-only and cannot be weakened by repo overrides.

No Hardcoded SecretsNever generate or suggest passwords, tokens, API keys, certificates, connection strings, or session identifiers. Approved secret-management patterns only.

No PII LoggingNever log customer data, account numbers, card numbers, secrets, session IDs, request payloads, or authentication headers — regardless of log level.

No Bypass InstructionsNever suggest bypassing auth, authorization, MFA, dual-control, change-approval workflows, audit logging, SAST, dependency scanning, linting, or tests.

Input ValidationValidate and sanitize all external input. Prevent SQL injection, XSS, CSRF, path traversal, unsafe deserialization, insecure redirects, and CORS misconfigurations.

Secure Error HandlingUse error handling that never exposes stack traces, internal paths, or sensitive system internals to end users. Error messages explain what went wrong, not how the system is built.

Human Review FlagsFlag auth, encryption, payment processing, audit logging, and PII-related changes for mandatory security review. These cannot be approved without a security team sign-off.
